# 三分钟演示讲稿

## 0 至 30 秒 说明问题

设备发出的消息不一定与程序一次收到的数据块对齐。一次读取可能只有半帧，也可能包含多帧；数据损坏时，程序还要定位问题并恢复接收。FrameTrail 用 MoonBit 实现这一层公共能力。

## 30 至 75 秒 正常编码和回放

执行 `node dist/frametrail.cjs encode 313233343536373839`，展示标准 CRC 测试载荷的帧。再执行 `node dist/frametrail.cjs replay examples/clean.hex 3`，解释每次只输入 3 个字节仍可恢复两条完整消息。

## 75 至 120 秒 故障诊断

执行 `node dist/frametrail.cjs replay examples/mixed.hex 3`，指出正常帧、[13,18) CRC 错误和第二个正常帧。强调数据是合成示例；返回 1 表示识别到坏帧。把 3 改成 1，结果相同。

## 120 至 155 秒 验证和工程边界

展示 `moon test --target js` 与 `moon test --target wasm-gc` 结果，以及 `python scripts/verify_reference.py`。解释生成测试、独立 CRC 参考和缓存上限。核心库跨目标，CLI 依赖 Node.js。

## 155 至 180 秒 贡献与下一步

COBS 和 CRC 本身不是新算法；项目的价值在于可复用的 MoonBit 实现、明确的错误恢复策略和可复现的诊断证据。下一步将用真实采集链路验证，并依据社区反馈完善适配器。

## 常见答辩问题

- 为什么用了 AI？AI 辅助设计、编码和测试，我需要理解状态机、协议和每项验证。未亲自掌握前不应作此完成声明。
- 能否直接读取任意串口设备？不能，设备须使用本参考帧格式，或先通过适配器转换。
- 是否保证不漏掉所有错误？不能。CRC 有碰撞可能，且没有认证能力；丢失分隔符还可能合并并丢弃相邻帧。
- 内存是否永远不增长？仅待解析缓存有界；返回事件和 CLI 完整报告由调用方按需管理。
- 已经用于哪些产品？目前只有合成数据与本地测试，不宣称客户、装机量或硬件验证。
