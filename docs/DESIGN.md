# 设计与可解释性

## 数据路径

传输适配器给出 Bytes → Decoder 按字节识别零分隔符 → 严格 COBS 解码 → CRC16 校验 → Frame 或 Rejected → JSON 回放报告。

协议编码只依赖标准库。CLI 文件 I/O 不进入核心库，因此核心库可在 JS 与 wasm-gc 复用。

## 三种运行状态

| 状态 | 输入和动作 | 后继 |
|---|---|---|
| 接收中 | 非零字节且未超限，追加缓存 | 接收中 |
| 接收中 | 非零字节导致超限，报错一次并清空缓存 | 丢弃中 |
| 接收中 | 零字节，解析当前段；空段只计数 | 接收中 |
| 丢弃中 | 非零字节，不缓存 | 丢弃中 |
| 丢弃中 | 零字节，更新下一段起点 | 接收中 |
| 任意未关闭状态 | finish，必要时报告截断 | 已关闭 |
| 已关闭 | feed 返回错误；finish 返回空数组 | 已关闭 |

字节偏移与事件不依赖 feed 的边界。超限在第 limit+1 个非零字节立即发出事件，因此改变切块长度不会改变报错区间。偏移采用 Int64；一个会话不应接收超过 Int64 可表达的累计字节量。

## 复杂度与资源

对于总输入 N 字节，编解码和校验为 O(N)；CRC 使用每字节 8 次位运算。状态机待解析逻辑缓存为 O(L)，L 是 max_encoded。解码时的输出和临时副本同样与当前段大小有关。CLI 为了形成完整报告，会保留输入和全部事件，不是常量内存应用。

## 为什么不用长度前缀

本版选择零分隔符与 COBS，便于在已知边界后恢复接收。长度前缀若被破坏需要额外同步设计；它有自己的适用场景，后续可独立实现为其他 profile。本版不混合多种无法自动区分的帧格式。

## 工程特色和边界

特色是把可复用编解码、资源限制、确定性诊断和故障回放组成一个小型组件，不是发明 COBS 或 CRC。没有进行全面专利或全生态查重，不宣称首创。有限检索中未发现完全同定位的 MoonBit COBS 故障回放工具，检索未命中不代表不存在。
